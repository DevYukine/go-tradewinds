# Architecture

## Boundaries

| Package | Responsibility |
| --- | --- |
| `cmd/tradewinds` | Explicit registration, account listing, Fx lifecycle, HTTP listener, worker startup and shutdown |
| `cmd/tw-sim` | Explicit account-scoped diagnostic backfill only; no game client or simulator |
| `internal/config` | Environment loading and validated operating limits |
| `internal/gameapi` | Current typed API contract, HTTP/SSE transport, scoped rate limits, retries and raw observations |
| `internal/store` | PostgreSQL migrations, encrypted credentials/journal, missions, snapshots, diagnostics, settlements and metrics |
| `internal/engine` | Economic decisions, durable mission execution, authoritative reconciliation and eligible reinvestment |
| `internal/sim` | Diagnostic path mapping, complete-page reconstruction and replay coverage reports |
| `internal/httpapi` | Bounded read-only views of database state, readiness and metrics |
| `internal/names` | Vendored canonical Pokemon catalog and unused-name selection |
| `web` | Next.js dashboard; no direct game credentials or game requests |

The Go process runs independently of the dashboard. Closing a browser does not stop trading. Opening more tabs does not create more upstream sessions. PostgreSQL is the durable operational record, not an optional cache.

## Account isolation

Each enabled account has its own credentials, company identity, mission namespace, event cursor, and executor. Credentials and action payloads are encrypted with AES-GCM under a local 32-byte master key; associated data binds ciphertext to its record identity. Dashboard data never includes decrypted credentials or raw action journals.

A pinned PostgreSQL advisory-lock connection protects account execution. Loss of ownership cancels the runner's context rather than transparently acquiring a new lock. Cancellation cannot undo an upstream request already sent, so a takeover must resolve pending journal entries before creating another dependent action. Company uniqueness prevents importing the same company under two independently executable local identities.

Monitor checks, write guards and cleanup serialize access to that pinned connection through the complete result-reader lifetime. A `database/sql` call returning does not mean pgx has released its active rows. This prevents false ownership loss from overlapping checks without suppressing real lock or connection failures.

## Mutation lifecycle

1. Refresh the relevant authoritative data.
2. Persist the mission and its immutable action identity/payload.
3. Send with that action's idempotency key.
4. Record the result durably.
5. Refresh cargo, stores, funds, contracts, or voyage state affected by the result.
6. Advance the mission from actual outcomes, including partial fills.

Network ambiguity is not failure evidence. A timeout or upstream 5xx retains the original intent. A successful response whose body cannot be interpreted is committed-but-uninterpreted, not permission to try again with another key. An in-flight 409 also remains unresolved. A definitive rejection may lead to a new, separately recorded plan after fresh state and any cooldown.

The upstream replay window is 24 real hours. Stop unresolved retries before that window expires, with a margin for in-flight request duration. Authoritative reconciliation must establish an outcome before a replacement action is allowed. Retaining the old key forever does not make it safe to replay forever.

Conflict recovery distinguishes definitive rejection from an ambiguous in-flight request. Freight tender refusals persist a bounded retry deadline; fresh active-contract and full-manifest evidence permit a new tender identity after that deadline. Fresh terminal contract states can settle the obligation without waiting for another tender. Charter refusals retain the observed offer terms and reopen when authoritative terms change. Response prose cannot prove a default, payment or delivery.

An attributed unresolved ship action quarantines dependent spending, not unrelated safe delivery credits. An orphaned pending request whose resources cannot be identified still blocks execution. Reconciliation and replay always use the persisted request's contract, ship and payload, never a replacement plan's identity. Short sealed manifests are held, not replenished with ordinary cargo or repeatedly tendered as the originally accepted amount.

Registration follows the same model. The generated passphrase is stored before registration; player creation, key creation, company incorporation, and company-key creation have stable independent action identities. A handle conflict cannot cause an automatic fallback name. Company creation is reconciled against the player's actual company list.

## Events and freshness

SSE is an invalidation channel. REST and settled action responses determine monetary state. Event IDs are opaque strings, not numeric sequence counters. Persist event deduplication and cursor advancement atomically. Reconnect with the recorded cursor; a replay gap requires cursor reset and authoritative resynchronization, not a loop using the same rejected cursor.

Publish a paginated dataset only after all pages succeed. Retain the last good value on refresh failure and publish an explicit per-dataset error/freshness marker. Refreshing the clock must not make stale cash or cargo appear current. Economic writes require fresh, coherent inputs.

The `loans` dataset paginates borrower-owned active and defaulted loans; an open loan action or financing intent also requires closed-loan authority for reconciliation. Publish only a complete response with the fields needed for debt reserves and collateral checks validated. Failed authority retains the last-good debt reserve and blocks new borrowing, not reserve-safe safety stores, sales, deliveries or docking. Debt reserves join regional cash requirements before discretionary allocation; the normative rules are in [Capacity financing](strategy.md#capacity-financing).

The low-frequency authenticated R&D datasets `rnd_status` and `rnd_register` read only `/v1/rnd/status` and `/v1/rnd/register`, at most once per account per 30 real minutes, including after failures. They retain last-good raw responses and dataset freshness/error metadata; owned patents, licences and component inventories are not fetched. The register is evidence for later rival analysis, not investment authority. The `rnd` decision records eligibility and estimated cost without authorizing research, patent, licence, manufacturing or fitting investment mutations. Identical details deduplicate, but changing player net worth normally produces about one decision per 30-minute poll.

R&D diagnostics currently use the generic two-minute stale display, not a dataset-specific expected-cadence mechanism. No such mechanism has been identified. Between scheduled 30-minute polls, a stale display without an error is expected and does not by itself indicate a failed fetch.

Each refresh runs independent GET jobs through at most six workers on the account's existing rate-limited client. Dependent waves still wait for their prerequisites; pagination and the explicit contract-status reads remain ordered within their job. Workers return private results and request timing. Only the runner reduces them into the snapshot, in deterministic order, after the wave has joined. Cancellation joins all workers and publishes no partial generation. Mutations remain serialized and do not overlap capture workers.

An actual CLI fixture capture completed 31 GETs in 0.519 real seconds; those requests' measured service times summed to 1.255 seconds. This is a local overlap measurement, not a live-game speedup benchmark or a separately run serial client. The same run observed six concurrent GETs, one mutation at a time, no GET/mutation overlap, and recovery after a `Retry-After: 1` refusal.

The runner must also wake without events for berth unlocks, cooldowns, deadlines, expected arrivals, and freshness expiry. Synchronous orders and unlocked berths are not guaranteed to produce the events a mission would need to progress.

Private books and shipyard quotes require fresh authoritative stationary ship presence or factor access. A sailing ship's retained origin and a mission's intended origin are not presence. Public route discovery remains separate from private-data authorization.

Successful public route responses are cached by origin, destination and hull for 24 real hours, retaining their original observation timestamps. The [route API](https://tradewinds.kibb.io/api-docs/openapi.json) returns static legs, distances and edge classes plus hull-derived expected/safe provisions and port consumption, not live hazards, prices or balances. Its default `max_phase` is the world's unlocked phase, so a phase change invalidates the cache, including known illegal paths. Refresh fetches only missing, expired or failed entries; cached geometry is usable across observation generations. Responses must match their requested endpoints and any requested hull class. The persisted route group drops unrequested pairs except the bounded illegal sourcing history described below. Books, quotes, vaults, ships, contracts, live hazards and every other executable observation retain current-generation freshness.

Clock bounds require a complete successful current-generation capture with valid request/completion ordering and a fresh host timestamp. Failed, future-dated or stale observations cannot authorize new mutations. A new-send preflight checks the same conditions after rate-limit waits; persisted ambiguous or completed actions retain their independent reconciliation path.

Ordinary queued events request another capture without indefinitely vetoing a safe mutation after the current capture. Stream gaps, authorization controls, and stream closure remain barriers: their published control epoch prevents writes against an earlier capture, even while a control waits behind ordinary events. Company billing, remittance, tax, seizure and bankruptcy events use a separate financial epoch. Captured spending decisions carry that epoch and the runner instance through staging. A stale never-sent request is replanned after authoritative refresh; an existing journal identity remains authoritative for ambiguous or completed outcomes. A first-attempt guard runs after the transport's rate-limit wait. If it vetoes a newly journaled request before transport, durable explicit no-send evidence permits safe replanning across restart. This guards known local invalidation, not atomicity with upstream cash changes.

Loan disbursement, repayment, default, collateral seizure, write-off, foreclosure surplus and insurance-to-lender payment events join that financial fence. They require refreshed debt, fleet and cash authority before new financial first sends; event payloads and balance changes alone are not loan receipts.

Invalidated never-sent standalone maintenance intents are released so idle planning can reconsider the ship from fresh state. Voyage missions retain their cargo and obligations; ambiguous or completed journal requests are never discarded by this release.

First-send monetary guards recheck fresh financial authority and the stage-specific funded commitment, including ship-less construction. Cash-funded construction reuses the planner's quote, payback, spare depth and commissioning-reserve checks; financed construction uses its frozen admission and live yard-ceiling, regional funding, debt-reserve and coverage checks. The transport callback checks the captured financial epoch both before and after that work, so a financial event published during preflight invalidates the never-sent request. Missing or failed balance observations cannot authorize a new debit; already attempted requests retain their immutable recovery path.

The published stream-control epoch also fences staging, preflight and the actual first send after a rate-limit wait. A gap or closure invalidates an earlier capture even if its balances still satisfy their age limit. Only an intent proven never sent may be released and replanned; attempted requests retain the exact durable identity and payload through reconciliation.

## Rate limits and retry ownership

The transport owns individual attempts, bounded transient retries, and rate-limit waits. The engine owns mission recovery, SSE reconnection, resynchronization, and economic replanning. Both use cancellation.

A process-wide public release watcher runs independently of account runners and trading, including when no account can trade. Its unauthenticated client reads the configured API's `/update` at startup and every 15 real minutes, with limiter feedback isolated from authenticated clients and a public cooldown capped at one hour. The first successful feed establishes the baseline even when empty; the first later release warns. Restarts establish a new informational baseline. A feed omitting the last-seen release is ignored without advancing its cursor. Polls emit at most five release warnings with bounded fields and headings extracted outside fenced code. Consecutive failures log once per streak and use jittered exponential retries starting within one minute and capped at one hour. This watcher neither blocks trading nor authorizes investment mutations.

| Bucket | Per-key burst / refill per second | Shared-IP allowance |
| --- | ---: | ---: |
| Read | 2000 / 100 | 5 times key allowance |
| Write | 1000 / 50 | 5 times key allowance |
| Batch | 300 / 10 | 5 times key allowance |
| Stream | 200 / 10 | 5 times key allowance |
| Authentication | Not key-based | 20 / 0.2 |

Authentication, stream routes, and batch routes must be classified before the generic HTTP method. Every retry consumes applicable tokens. Apply cooldown to the affected bucket rather than blocking all reads and all accounts unnecessarily. Respect `Retry-After`; a cached mutation 429 is not a reason to rotate an ambiguous action key.

SSE scanner errors preserve their original cause. Only `bufio.ErrTooLong` is reported as the 1 MiB line limit; interrupted chunks and connection failures are transport errors handled by the existing reconnect policy.

These shared-IP limiters coordinate one process. Separate hosts or processes behind the same public IP still share the upstream allowance; PostgreSQL ownership protects a company, not the entire network's request budget.

## Persistence lifetime

Raw request/response diagnostics, event payloads, and decision traces have a seven-day retention window. Current snapshots, encrypted credentials, mission recovery state, unresolved actions, idempotent settlement records, and metrics survive that window. Action journals are operational recovery records, not disposable request logs.

Goose version 9 adds the replay tape, separate from capped seven-day diagnostics. `replay_payloads` stores redacted dataset bytes once per account using streamed, purpose-separated HMAC-SHA256 digests, gzip and AES-GCM; unaffected bytes stay exact. Events use a separate digest domain and uncompressed encrypted storage to avoid a mixed-trust compression oracle. Aggregate frame plaintext and decompression are bounded at 16 MiB, with a 4 MiB gzip cap. Frame preparation bounds raw evidence before parsing and bounds the redacted representation again, so credential replacement or JSON escaping cannot create a permanent oversize failure. Largest datasets become reasoned metadata-only gaps; metadata/name-only overflow becomes a compact frame gap instead of stopping either recorder. Live losses increment the process-local recorder error counter and warn once per account/cause. Encrypted compressed `replay_frames` manifests bind dataset keys and `DatasetMeta` to those digests. Payload locks and last-seen updates share the frame transaction; sorted digests and batched inserts avoid random lock ordering and ciphertext round trips. Manifest AAD binds a random portable capture identity and all semantic headers, not bigserial IDs, allowing authorized transfers between databases without unauthenticated clock, source or timestamp edits. Only validated public clock scalars are plaintext; fields with unexpected types are omitted independently while raw clock evidence remains encrypted. `ScanReplayFrames` keyset-pages by `(observed_at, id)` and retains only the preceding frame's decrypted digest cache.

`replay_plans` is append-only accepted plan and policy evidence, with ship, phase, revision and plan context encrypted together and generation, sequence and observation time authenticated. The recorder deduplicates the same semantic private tuple as the store. `replay_action_links` joins persisted mission/action identities without copying the authoritative mutation journal. Both survive tape pruning; account deletion cascades through all four tables. Replay writes use `Store.query`, never executor ownership guards, so a timeout cannot cancel the live lease.

Each runner has one five-second-deadline background writer and a four-frame queue. The runner captures immutable byte references and frame-only runner metadata, with pass-start observation times, before another pass can mutate its maps; cached raw quay-port bytes avoid ordinary-frame ports/routes decoding. Competition stays outside operational snapshots, and event/competition serialization runs on the writer. Mission saves buffer changed plans and action links after successful authoritative persistence; failed writes clear dedupe entries for later captures. Startup imports existing evidence without marking a new decision. Frame saturation is counted without database I/O using process-lifetime `replay_record_errors_total` counters. Pending decisions survive decimation; the next pass after a decision preserves post-action observations. SSE retention is bounded to 256 envelopes and 1 MiB, with overflow counts and incomplete metadata. The writer recovers panics and drains only after explicit stop, with a bounded timeout and counted drops; it cannot fail `Run` or authorize a mission transition.

`REPLAY_RETENTION_DAYS` defaults to 90 real days; zero disables recording and tape pruning. `REPLAY_MAX_GIB` defaults to 20 GiB of encrypted payload and manifest bytes. Last-seen payload updates coalesce within one hour to reduce indexed writes and WAL; hourly pruning applies the same conservative slack, computes a newest-first cumulative byte cutoff and deletes whole oldest frames in 10,000-row batches. The slack can remove extra near-boundary frames to enforce the cap without dangling payload references. Plans and links are not capped. Logs also report physical relation size because logical tape bytes omit TOAST, indexes and dead tuples.

`tw-sim backfill --account <label-or-ID>` freezes diagnostics before the first live frame or at the initial maximum request ID. Indexed completion-time keysets fetch 5,000-row batches; a frozen REST duration window capped at the client's 45-second timeout plus one second of diagnostic slack releases them in exact request-start order without rescanning history. Event-stream lifetimes are excluded, and out-of-timeout diagnostics are reported as skipped gaps. These batches and hourly route `GROUP BY path, md5(response::text)` aggregates use statement timeouts; route versions merge across windows in memory while retaining each window's first/last observation times. Tape-ordered sightings use the shared 24-hour `RouteGeometryTTL` when retaining route keys. Failed clocks still delimit passes. First-wave anchors accept a staggered whoami after the previous clock completed when there is no later-wave completion, or any first-pass whoami. URL-parsed production query names and complete cursor chains reconstruct datasets, with complete loan statuses required and partial contract scopes disclosed. SSE rows stream through 256-row keyset pages into pass assembly; the live 256-envelope/1 MiB buffering caps apply during consumption, rejected payloads are released and dropped evidence is disclosed. Remote ports decimate to five-minute bins. Oversize dataset gaps, including post-redaction demotions, are counted in the coverage report. Current catalog data is marked assumed, missing/truncated data stays a gap, and deterministic diagnostic generations are unique only for backfill. See [Replay recording](runbook.md#replay-recording) for coverage limits, operation and backups.

SSE ingest and live replay capture share a `UseNumber` token walk that replaces numbers with an exponent beyond plus or minus 32, numbers longer than 32 characters, and nesting deeper than 64 levels with reasoned payload gaps. Ordinary floats such as `2.5e-7` are kept. Identity, type, receive time and cursor semantics are preserved without sending the rejected numeric tokens to PostgreSQL.

Event pages bound stored JSONB size and preflight nonzero numeric magnitudes outside `1e-100` through `1e100` without rendering before checking normalized UTF-8 size. Guarded and oversize rows retain only gap identity/time/size fields for dropped-evidence accounting. Backfill sweep routes share `SourcingRouteRetentionLimit`, `SourcingRouteRetentionBytes` and `SourcingRouteRetentionScanLimit` with live snapshots: newest first, key-order ties, 256 optional routes, 1 MiB including escaped route/metadata entries and at most 1,024 candidates. These caps preserve core datasets instead of allowing optional history to replace a whole frame with a gap.

Official standings are a permanent metric. Goose version 8 creates `standings_history` and `standings_accounts`, backfilling distinct successful retained leaderboard responses and current account snapshots in its transaction. Later successful `GET /v1/world/leaderboard` recordings persist standings atomically with the scrubbed request diagnostic; no engine or extra game request is needed. `(season_number, refreshed_at, rank)` identifies one published player observation, deduplicating repeated polls and accounts without overwriting an hourly valuation. Caller mappings retain `you` even outside the public top 20. These tables are never pruned with seven-day diagnostics; already-expired raw responses cannot be recovered.

Runner decision fingerprints use a bounded 2,048-entry cache with seven-day deduplication. Sourcing emits an aggregate count and at most three ranked details; only the rolling arrival estimate is excluded from the fingerprint, not the persisted diagnostic. Cache eviction can repeat a diagnostic but cannot discard recovery state.

Diagnostic sanitization covers JSON member names as well as values, including nested event/request payloads and snapshot dataset names. Known account credentials, bearer tokens, API-key patterns, and credential assignments are scrubbed before persistence, so the same protections apply to history and dashboard read surfaces. Colliding sanitized member names receive distinct numeric suffixes without overwriting existing public names or dropping their values.

Realized economic records use integer pence and stable settlement identities. Graph metrics may use floating-point values for presentation; they are not the ledger. Seed capital, remittance principal, borrowed principal and collateral refunds are not trading income. Loan principal repayment is financing cash outflow, not voyage expense; interest and transfer fees remain distinct from principal. Capacity financing checks interest-adjusted net separately from installment cash coverage.

Mission accounting keeps durable claims on observed ledger expense IDs so a company-wide charge is not deducted by every concurrent voyage or charged again after a restart. Unknown acquisition costs remain unknown; they are not zero-cost profit. Reinvestment consumes known-cost settled results, including losses, rather than a filtered history of winning trades.

Goose version 5 converts mission metadata/recovery bytes, settlement context, policy payloads and owned-slice identity/frozen terms to authenticated ciphertext. Purpose-separated, length-framed HMAC-SHA256 lookup keys replace sensitive external identifiers in indexes; numerical accounting and bounded local classifications remain queryable. Associated data binds ciphertext to its account, table, field and lookup identity. Dashboard, history, Journal and console projections still scrub decrypted display strings before exposing them.

The conversion and version entry share one transaction, block legacy table access and refuse active account/company executor leases. It authenticates all existing credentials and writes a singleton key verifier; subsequent opens compare that verifier in constant time rather than treating a wrong lookup key as an empty database. Missing or corrupt verification data fails closed. Existing action ciphertext is not rewritten. Legacy nested action bodies are converted once, using exact journal bytes when the bound action and semantic payload agree; steady-state recovery has no plaintext compatibility reader.

During that conversion only, a legacy `__growth` control with an absent or null lane receives an explicit zero-quantity, zero-procurement allocation marked complete and tied to its existing generation. Existing allocations and unknown recovery fields are preserved. The controller resolves any original attempted action before accounted withdrawal; it neither synthesizes new lane economics nor sends fresh commissioning debits for that marker.

New destination-completing missions explicitly persist that choice; older roundtrip missions keep their existing return semantics. Sourcing uses a durable zero-revenue relocation mission and separate settlement before cargo handoff. Permanent history charges every probe, including failed inspections, rather than using the dashboard's recent rows. Nullable exploration expense separates consumed-store exposure from full provisioning cash; legacy known-cost probes retain the conservative full-cash upper bound. Unknown commercial costs prevent profit-based replenishment, while unknown probe spending blocks further use of the seed.

Ballast scouts reuse the relocation mission with a durable `scout` marker, idle-pilot marker, immutable expense cap, physical store basis and `target|origin|commodity|scout` completion lane. After 12 coherent idle game hours, designate the smallest-free-hold eligible co-located ship (then ship ID), subject to its own admission, insurance-compatible accepted candidate and one relocation fleet-wide. Public bid hints at most 168 game hours old rank candidates only; no executable depth, cargo quantity or revenue is fabricated. Other fleet presence, final sailing destinations, unsettled non-maintenance mission destinations and complete quay observations less than 6 game hours old exclude targets. `_book_observed` is a replayed planning input, retained across departure for the longer of 24 real hours and 168 game hours, unless the catalog removes its port; it supersedes older or equal-aged hints. Provisions supply evidence is mandatory at target admission. The bounded probe summary persists per-target completion/departure timestamps, a fleet scout counter and its reset timestamp: two completed, unconverted scouts stop admission until a laden departure from a port whose scout completed after the last reset, never merely idle hours or repeat departures from old scout ports. Target cooldowns span all origins for 24 real minutes and also exclude recently departed ports. Scout lanes update ship streaks and scout controls, never charter source history. Funding, provisioning and departure recheck blocked targets and hint upside versus exposure without repeating admission-only provisions-gossip-age gates; spending is bounded by both the immutable cap and current sourcing allowance. Only positively classified database, freshness, history and clock faults hold a funded intent, for at most 30 real minutes using a persisted hold start cleared on successful progress. Other failures and expired holds durably cancel into closing before further spending. Costs omit the charter inspection wait while retaining both-way route, hazard, berth, stores and funding checks. Authoritative arrival closes without source inspection or cargo handoff.

Sourcing excludes known illegal source-to-charter and return legs before ranking. Exploratory pair captures, including expired illegal pairs, share a three-new-pair, six-GET budget per pass. Committed relocation legs are captured first, outside that discretionary budget, so exploration cannot prune a mission's required continuation. Only a pair that queues a GET consumes an inspection; fresh retained geometry and already attempted failures do not. It validates the actual current-port-to-source-to-charter itinerary, not an unused direct current-port-to-charter shortest path, so legal coastal detours remain eligible.

Fresh edge, zone-class and Sound-toll rejections for a current non-sunk fleet hull remain eligible for optional history only between a public source candidate and a non-stale open charter's origin, even if sourcing skips the ship for a mission, admission gate or full shortlist. Charter rewards and public supply hints are indexed once per pass; at most 1,024 newest optional route candidates are checked. Rejected exploratory pairs, including legal pairs rejected for continuation stores or deadlines, share the same 256-directed-route, 1 MiB history cap including metadata. Newest observations win, with lexical key tie-breaking. Before persistence, oldest optional entries are evicted in batches until both the raw input size and the exact redacted encoded representation fit 64 KiB below the store's 8 MiB limit, or no optional history remains. The store shares its serialization and credential-redaction path with the size measurement; the engine remeasures after every batch because redaction can expand short sensitive values. Required presence, committed mission and validated shortlist routes are not evicted as history. Original metadata, the 24-hour TTL and phase-change invalidation remain unchanged. Other unrequested legal routes, incomplete classifications and yard-only classes are pruned. A retained oceanic leg for a coastal hoy is a definitive hull rejection, never a request for another fresh public quote; legal regional candidates retain the existing stores, funding and exposure checks. No legal candidate means a clear rejection rather than an unsafe departure or invented opportunity.

Physical idle state is a durable account/ship-local snapshot projection of the last validated game hour, port, server clock and earned idle hours. Previous and current clock observations must both pass the existing freshness/coherence rules to earn a delta; invalid or stale gaps rebase. Maintenance and intent selection preserve the record, while authoritative activity resets it. The same per-ship policy controls both bounded source refresh and execution. Verified canonical and legacy probe completions provide the real-time revisit cooldown; every permanent probe expense still consumes the selected, non-additive risk allowance. A persisted idle-pilot marker and immutable expense cap bind staging and first-send spending checks.

After a stale gap or UTC rollback, a later advancing frame establishes a new baseline without crediting downtime; an identical cached frame cannot establish it. An unattempted origin pilot must still qualify as idle and yield to newly funded ordinary income. Its actual provisions IOC quantity and limit must fit both the durable cap and the current reduced allowance. Attempted requests, acquired cargo and necessary safety recovery keep their existing protections.

`EconomicHistory` remains the permanent loss-inclusive accounting view. `GrowthHistory` adds a separate inclusive 12-hour host-recorded cohort, evaluated with one UTC `asOf` for account and lane aggregates. Exact SQL numeric sums include whole qualifying settlements without a display-row limit; future relevant completions veto the proof before upper-bound exclusion. Growth recomputes this window at first send, while active liabilities and durable owned-hull commissioning remain independent of the cohort.

Ordinary voyage pricing and funding share checked regional cash requirements. The optional `funding_fees_pence` economics field is a nonnegative modeled cost already included once in expected net, stress, repeat net and rate. Mission-owned transfers preserve paid fees across repricing or zero-cargo withdrawal; company treasury control cannot fund an uncommitted destination first. Indivisible freight IDs are reserved across missions as well as cash and quantities. Never-sent actions retain the existing financial-session replan fence; attempted actions retain their exact journal identity and payload.

Voyage-specific funding, docking and provisions revalidate the pinned opportunity, including freight listing expiry, before staging and first send. Independent maintenance is not contingent on a trading opportunity: its docking purpose is stored with the durable action, not inferred from missing guns or low stores at send time. A still-needed immutable remittance may partially fund a deficit enlarged by accruing dues: donor reserves must remain protected, the residual deficit must remain fundable, and paid, proposed and remaining fees (including separate-transfer rounding) must preserve positive contribution.

Growth retains its admitted marginal lot and capital reservation through construction, provisioning, refit and atomic handoff to the actual built ship. The handoff also carries paid operating cash, cost certainty, ledger boundaries and terminal-action evidence. Rejected, aborted and sunk commissioning controls settle their paid costs and attributable bills before deletion; hull and gun investment remains separate from operating shipment net.

Ordinary and growth planning share one owner-excluded reservation view for cash, source asks and stores, destination bids and charter quantities, including the next lot reserved during a paid return. Growth consideration and first-send build checks also evaluate idle hulls against those residual opportunities, excluding only the proposed growth allocation. First-send procurement must still fit residual asks at its immutable price limit. An unattempted ordinary purchase whose fresh residual depth is insufficient unwinds its paid costs and replans instead of repeatedly staging the same unsupported quantity; attempted requests keep their original identity and payload. Changed accrued-dues quotes are saved and execution continues in the same pass; quotation uses planned funded armament, while actual refit and departure checks use authoritative ship state.

An optional empty return needs fresh executable source/destination evidence and a persistently reserved next lot that beats local work after future return costs; it is not an unconditional route loop. After the paid return, the controller safely docks to inspect the source and re-prices before buying. Partial or zero IOC results are final for that order. Paid-cargo unwinds retain their loss-inclusive settlement instead of disappearing from future growth or discovery evidence.

Underwriting has its own `__underwriting` control mission, restored before orphan-action checks. The ordinary immutable journal owns retries; an unresolved slice reserves full possible collateral without disabling unrelated safe fleet work. Public policy observations, immutable owned receipts, funding provenance, terminal accounting and the fixed pilot seed are permanent PostgreSQL records. They are not pruned with seven-day diagnostics. A public membership filter is not an owned-slice receipt, and a policy disappearing from a listing does not release collateral. Additional risk waits for an exact owned-vault ledger debit; closure requires unchanged terminal policy evidence, not elapsed time.

Permanent changed-term or contradictory policy evidence vetoes both candidate admission and first send, even if the public board later reverts. A disputed prior settlement cannot release the pilot's risk capacity. Shipping commitments protect regional deficits and measured remittance fees before underwriting receives discretionary cash. Exact receipt identity, ownership and monetary bounds are validated independently of public coverage.

Letters of marque use a `__marque` control mission on the same immutable journal. An unresolved issue reserves its home-vault cost but does not block unrelated ship work; it does veto a concurrent hull build. Finished marque outcomes are merged into the working snapshot for the realized stop. Capacity growth reuses the `__growth` control with a `Capacity` intent instead of a frozen lane: build, arm, settle and delete, leaving the hull to ordinary planning.

### Capacity financing

The normative admission, reserve and servicing rules live in [Capacity financing](strategy.md#capacity-financing). Goldsmiths financing belongs to the existing `__growth` mission. Durable `Capacity.Financing` state holds exact quotes, accepted loan receipts, frozen admission values and the package's incremental regional cash protection through funding and construction.

`growth_finance` stages `loan-accept`, refreshes authority and funds the yard before `growth_build`. The first receipt establishes a durable `BuildBy` deadline. Canceled financing retains unused debt in `growth_finance_repay` until repaid; active arrears use `loan-repay` under the reserved `__loans` control mission without replacing `__treasury`. Each action has its own immutable payload and idempotency key, and ambiguous actions reconcile before their phase can be replaced.

Loan receipts, not vault movements, establish disbursement and repayment. A matching-identity HTTP 200 acceptance records the debt even when terms changed, allowing cancellation and repayment rather than a permanently attached action. A matching named-loan HTTP 200 repayment is authoritative despite intervening automatic collections. Lost responses reconcile from the named loan under the strategy's receipt rules. Borrowed principal is not revenue, principal repayment is financing cash outflow, and interest and transfer fees are accounted separately.

## Dashboard contract

The browser reads `/api/dashboard` and bounded `/api/history` views through Next.js rewrites to the loopback Go API. TanStack Query owns fetched state; Zustand owns local controls such as account selection and map filters. The map uses explicit geographical port coordinates because the game catalog does not provide latitude and longitude.

Every view must distinguish a real zero from missing, inaccessible, stale, or failed data. Market estimates and inventory valuation must identify their basis. Source timestamps govern freshness; browser fetch time alone is not enough.

### Engine warnings and build identity

`Store.Warnings(ctx, at)` projects the relevant recorded snapshot fields for enabled, registered accounts in one read-only transaction: `_engine`, `_meta`, ships, clock, catalog ports and grouped ship details, plus recorded arrival/departure evidence where needed, the latest ten known-cost commercial settlements, and the 24-hour growth benchmark. It does not load the entire large snapshot for this view. Pure `AssessWarnings` applies named fixed thresholds and display scrubbing; it neither calls the game nor changes engine behavior. Critical warnings sort before warnings, then by code and subject. [Engine warnings](runbook.md#engine-warnings) is the operator threshold/source/action reference.

The six codes are `controller_stalled` (critical, completed `_engine.observed_at` at least 10 real minutes old, missing engine yields none, suppresses refresh), `refresh_failing` (critical, any ships/vaults/contracts/clock update at least 10 minutes old with a current controller), `fleet_idle` (at least half of known non-sunk ships, minimum one, docked/no voyage/free to depart at least 30 minutes), `hold_stuck` (longest qualifying ship-level hold after at least 90 minutes free, excluding account/control holds and counting other stuck ships), `loss_streak` (latest three known-cost commercial completions all strictly negative), and `falling_behind` (24-hour change negative and below a median of at least three measured rivals, latest publication at most two hours old). Commercial kinds are exactly `spot`, `charter`, `freight`, `spot+freight`, `charter+freight`, `recovery` and `aborted`; probes and unknown costs are skipped.

Idle/hold assessment requires complete, error-free, non-stale ships and engine snapshots with `updated_at` less than two real minutes old, an unpaused clock and non-observe mode. An all-unknown fleet (`known=0`, `unknown>0`) is unassessed. Free time starts after the later docking and turnaround-unlock timestamps, using `berthed_at` or `dock_queued_at`, then a newer grouped `data.ship_details[id]` observation if absent; its metadata key remains `ship_details/<id>`. The final fallback is the latest recorded `ship_arrived.created_at`, only after the latest departure and while fresh state still says docked/no voyage. Its `names.since_source` is `arrival_event`, and presentation labels this as since recorded arrival (receipt time). Missing time stays unknown and is excluded from the known fleet denominator, never treated as idle.

The arrival fallback selects only docked/no-voyage ship IDs that still lack docking-clock evidence after the shared grouped-detail preference. Its newest-first arrival/departure query is bounded to seven days and 10,000 rows. Transactional Goose migration `00011_warning_arrivals.sql` adds `events_warning_arrivals_idx ON events (account_id, created_at DESC, id DESC) WHERE event_type IN ('ship_arrived', 'ship_departed')`; the query uses this exact predicate so unrelated account events are excluded from the index scan. Up/down use `IF NOT EXISTS`/`IF EXISTS`, leave event rows untouched and commit atomically like version 10. A truncated history can leave a ship unknown but cannot hide a departure newer than a retained arrival.

`GET /api/warnings` returns `generated_at`, real `build {revision, modified, started_at}`, `accounts [{account_id, label, available, error_code, suppressed, warnings}]` and `unmonitored [{account_id, reason}]`. Disabled, unregistered and empty-API-key registrations are explicitly excluded with reasons `disabled`, `unregistered` and `no_api_key`. Account-local corrupt credentials, malformed snapshots or oversized snapshots leave healthy accounts available in HTTP 200 and use only safe `error_code` values `credentials_unavailable`, `snapshot_invalid` or `snapshot_too_large`; corrupt credentials remain monitored, not unregistered. Each warning carries `code`, `severity`, `since`, integer `facts`, scrubbed `names` and `reason`. Revision comes from `runtime/debug.ReadBuildInfo`'s `vcs.revision`, or is null; modified is the actual VCS flag and started_at is process start, never invented from a requested filename. Nil storage or a failed database read returns 503 `database_unavailable`, not a successful all-clear. The startup `dashboard API listening` INFO line includes the same revision/modified identity.

`suppressed` identifies codes whose evidence was not assessable, not healthy conditions. Missing/zero/future engine time suppresses controller and refresh; a valid stalled engine raises controller but suppresses refresh. With a current controller and no qualifying stale refresh timestamp, missing/zero/future required dataset timestamps suppress refresh. Stale/incomplete/errored ships or engine, pause/observe mode and an all-unknown fleet suppress idle/hold. Missing/stale/invalid 24-hour endpoints, missing our change or median, or fewer than three measured rivals suppress falling-behind assessment. Fewer than three known commercial completions is an assessed negative for loss-streak, not unavailable.

The process-wide watcher is independent of account runners, evaluates immediately and each real minute, raises WARN `engine warning` once per `(account_id, code)`, repeats WARN `engine warning persists` when an assessed active key has not been logged for 30 real minutes, and clears once at INFO with `active_for` only after an available, unsuppressed negative assessment. Changing facts does not re-raise an active key. Missing accounts, account-local failures and suppressed codes retain prior state without false clear/raise transitions. Global read failures emit WARN `engine warnings unavailable` once per streak with safe `error` (`database_unavailable` or `context_deadline_exceeded`); account-local unavailable streaks include account identity and safe `error` derived from the account error code. Cancellation is silent. Restart establishes a new in-memory baseline and raises measured active warnings once. Logs retain transitions, not a new warning-history table.

The browser shares one global 30-second warnings query and renders only its current report. Successful responses do not retain earlier warning lines for missing/unavailable accounts or suppressed codes; that retention belongs to the log watcher, not the UI. Actual warning lines and genuine unavailability for monitored accounts appear on every view. Explicitly unmonitored accounts, including empty-API-key registrations, get only an Overview not-monitored note rather than a missing-evaluation error. Suppression/not-assessed notes, quiet all-clear and build context are Overview-only; a nonempty fully assessed monitored scope is required for all-clear. Other views render nothing without actual warnings or genuine monitored-account unavailability. A request failure alone keeps the cached last successful response with a could-not-update note, or says `Engine warnings unavailable` for monitored scope if no response was cached. No warnings is not proof of profit.

[Fast restart](runbook.md#fast-restart) stages builds, preflights binary VCS metadata and limits shutdown to executable paths under the delivery directory. Default deployments reject tracked Go changes, then build the captured HEAD revision in a temporary detached Git worktree with checkout hooks disabled. Cleanup runs in `finally` with double-force removal, one retry and registration pruning; cleanup diagnostics preserve an earlier build error. Builds disable workspaces, set the nonempty `GOFLAGS=-mod=readonly` to override saved flags without discarding other persisted Go settings, and use `-mod=readonly`. Native Git/Go calls check exit codes with nonterminating error handling for Windows PowerShell 5.1 redirected-stderr compatibility. Automatic reuse requires the full HEAD revision and `vcs.modified=false`; otherwise the script rebuilds. `-AllowDirty` always rebuilds the working tree under a `<hash>-dirty` name. Explicit `-Version` rollback may select a modified or metadata-incomplete artifact with a printed warning, but a present revision must match its requested prefix. The Ctrl+C helper checks exclusive console ownership before broadcasting, otherwise waits for the selected-PID forced fallback. Explorer owns the replacement console. Normal success requires readiness, the new executable process path and matching API build identity; explicit legacy rollback can report `running, revision unverifiable` after readiness/path confirmation. This is an operator command, not a crash supervisor.

Verified replacements are installed before shutdown unless the target path is the running image. Same-version replacements then launch from their retained, process-selectable staged filename. A later restart promotes the newest verified staged artifact to its canonical versioned filename once neither path is running, without replacing a newer verified canonical build; stale nonrunning staged files are pruned while running images and the latest pending replacement are preserved. Once shutdown begins, failure handling preserves the verified executable and prints the exact manual relaunch command rather than deleting the replacement. Printed command arguments use single-quoted PowerShell literals with doubled apostrophes, preventing directory names from becoming expressions when pasted.

### Recorded dashboard views

Competition uses `/api/competition?account_id=…`, a read-only, account-scoped rolling **24 real hour** summary. `Store.Competition` combines at most 10,000 retained `ship_sailed` / `ship_entered_port` events with current port snapshots in one repeatable-read transaction; it never scans request diagnostics or calls the game. The partial `(account_id, created_at DESC, id DESC)` sailing-event index bounds the receipt-time lookup. Upstream event timestamps and REST `seen_at` determine the inclusive activity window, so replayed old notices do not look fresh. Reaching the row limit is disclosed as truncated evidence.

The exported pure `AggregateCompetition` accepts typed observations for later engine use. Notice identity is `(time, port, company name, ship name, direction)` across SSE and REST; ship identity is `(company name, ship name)`, not a hull UUID. Regional totals union identities across their ports rather than summing port counts. All configured companies, including disabled accounts, are excluded by their retained profiles; unresolved company names leave foreign counts unknown. Reported route endpoints are preserved separately and never treated as direct sightings or current positions.

The runner's lightweight competition read supplies its current in-memory company profile before the final snapshot save. The account's stored company binding still validates that identity; other configured accounts retain their stored profile projections. This keeps first-pass competition evidence available without a second large snapshot write, while snapshot sizing includes the new replay input keys.

Identity coverage is always partial, never a world census. A dated quay sample or a named notice establishes observed evidence; without either in the window, company/ship counts are null (`not_observed`), not zero. An empty dated quay sample may show zero, explicitly only for the observations available. Current source timestamps, missing public metrics and stale/failed port sources remain separate; port observations at least two real minutes old are marked stale. Public rolling tons/turnover include us and have no documented window. The World view shows one calm region list with native [disclosures](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/details) for ports. Each port shows compact public metrics and at most five company rows ranked by ships seen, with latest sightings and an overflow count; individual ship details stay out of this view. One TanStack Query cache per account polls every 30 seconds only while visible; stable [React keys](https://react.dev/learn/rendering-lists#keeping-list-items-in-order-with-key) preserve open rows on refresh. It inherits the shared Plex typography and nautical light/dark tokens instead of adding statistic cards or a second map.

Money history uses `/api/money-history?account_id=…&range=24h|7d|30d|all|custom`; both account and range are required. Custom requests require inclusive RFC3339 `from` and `to` timestamps, including their timezone, with a nonzero `from` and `to` after `from`. Presets end at the API's current host time; All starts at the first recorded observation. A repeatable-read transaction returns the resolved bounds, generation time and automatic UTC bucket width. Each cash, net-worth and overlapping-ledger series retains its last actual observation per bucket independently (at most 481 samples per series). Epoch-anchored buckets do not depend on the database session timezone. Bounded lateral index probes find the first observation and each bucket's latest sample without sorting or counting the full metric history. Ledger snapshot totals must never be added together.

Settlement periods aggregate durable settlement accounting directly, not the latest 500 mixed metric rows: frequent balance snapshots previously crowded almost every realized-net point out of the dashboard. Gross includes all recorded proceeds; acquisition/fees/provisions/expenses and net include only known-cost completions. Unknown-only periods return null costs and net, never zero-cost profit. Each period's `at` and `to` are clamped to the requested bounds and shown as an interval, including partial edge buckets. No empty periods are fabricated. Arithmetic aggregates exact PostgreSQL numeric pence before checked integer projection; chart rendering is a presentation, not the authoritative ledger. Cumulative net starts within the selected range and excludes unknown costs, unfinished voyages and unallocated company expenses. Current treasury and ledger data are overwritten snapshots; metrics retain their observed history. Historical net worth is currently unrecorded and remains explicitly missing rather than reconstructed from current standings.

The single money plot has a metric switcher and persisted 24h/7d/30d/All presets plus custom UTC date-and-time controls. Custom inputs remain local drafts until Apply range commits valid bounds; historical custom ranges do not poll. The interaction follows [financial range-selector guidance](https://www.highcharts.com/docs/stock/range-selector): quick presets plus precise date inputs. A second overview/brush is deliberately omitted to keep touch and keyboard operation simple and avoid another chart. Gain/loss bars use shared theme tokens, signed values and above/below-zero position; the keyboard point inspector and value table provide [non-color and textual alternatives](https://www.w3.org/WAI/tutorials/images/complex/). The vertical axis covers the recorded range and zero using round 1/2/5 steps in whole Crowns; exact pence remain in the inspector and table. Loading and failed retrieval are distinct from missing observations. Balance freshness warnings apply only to ranges ending near the response's generation time, not deliberate historical views. Background refresh and pointer inspection do not repeatedly announce changing values. The existing Plex typography and nautical neutral surfaces stay quiet around the working chart.

World > Standings reads `/api/standings-history?account_id=…&range=24h|7d|30d|all&top=5`; `top` accepts 1–20. It uses inclusive official valuation times and the same preset control, monetary axes and chart styling as Money. The chart defaults to our latest recorded company and the directly adjacent ranks from that same official snapshot, requesting the available top 20 to find those rivals. Top 5/10/20 plus our player remain selectable. Accessible legend toggles hide individual lines and rescale the axis to visible series. Repeatable-read summaries calculate exact first/last integer-pence changes before downsampling. The API deliberately retains its exact first/last values, observation count and change as range summaries, distinct from Rivals' fixed 24-hour comparison. Each charted series has at most 481 last-per-UTC-bucket observations plus its exact first observation; missing intervals remain missing. A single observation has null change, never an invented zero. Our player has a heavier solid line, and the full official standings and valuation-method disclosures remain available below the chart.

The [official leaderboard contract](https://tradewinds.kibb.io/api-docs/openapi.json) recomputes every real hour and publishes best-company names, home ports, integer net worth and titles, but **no player handles or IDs**. The runner fetches it with each full reconciliation (a normal idle wake is at most 15 real seconds, with event/action-driven wakes sooner). Historical series therefore remain separate by season and published best-company name: no guessed joins across renamed/replaced companies or seasons, and no reconstructed valuations before retained evidence. Source refresh/next-refresh times determine the explicit stale state, not browser fetch time.

The Rivals block adds a two-row Growth vs rivals table ahead of three qualified hunch lines and one searchable comparison table. `/api/rivals?account_id=…` reads saved evidence in one read-only repeatable-read transaction and never calls the game or scans request diagnostics. Hunch change compares the latest official publication with the nearest publication in the same season within 60 minutes of 24 real hours earlier. Missing names or publications leave change null; a name first valued less than 24 hours earlier is too new, otherwise it is unmeasured. Identity is the exact `(season_number, company_name)` pair, with no fuzzy matches or inherited values between similarly named companies. Known configured company names and the account's `standings_accounts` name are excluded. When own names are incomplete, the observed list may include our other companies, so all three verdicts are withheld with reason `own_companies_incomplete`. Historical names absent from both the latest publication and 24-hour traffic are omitted.

`RivalReport.growth` returns 6-hour then 24-hour windows. `growthBenchmark` matches the baseline publication nearest `t1-window` within plus or minus 60 minutes, always in the latest publication's season. `from`/`to` are matched source timestamps or null, not fabricated target times. Our endpoint `standings_accounts` identity must exist at both times and have the same best-company name; otherwise our change is null with a reason. Rival endpoint gaps count as unmeasured. Each window exposes integer-pence our change, median, top rival/change, measured/unmeasured counts and our place among us plus measured rivals. An even median averages the middle two changes with truncation toward zero; no measured rivals leaves median and top null. This measures official valuation change, never realized rival or own profit. Only the 24-hour window feeds `falling_behind`; 6 hours is UI-only.

Hunch precedence is `most_dangerous > plays_rough > threat > losing_value > growing > steady > too_new > unmeasured > not_ranked`. Most dangerous is the largest rival above our same-publication net worth with at least one shared lane or port; only unknown overlap permits the largest-above-us fallback. Threat requires at least our net worth and observed overlap. Neither applies when our valuation is missing. A positive measured change is growing and zero is steady, even if net worth remains negative; the negative-worth fact preserves that distinction. Otherwise negative net worth or a negative measured change is losing value. Rows follow hunch precedence, then net worth descending with missing values last, then exact name. The three verdicts are selected independently of the row's one hunch and fact.

Plays rough uses attributable evidence, strongest first: an in-force, unexpired monopoly from a complete, error-free snapshot updated within 30 real minutes; the count of recorded monopoly grants in seven days; the latest recorded borrower record's positive walk-away count; then its positive default count. Missing or zero credit records and stale or expired monopolies do not establish rough play or a clean record. Evidence only for companies outside the listed rivals yields `unlisted_only`, not a claim that no rough play was recorded. The headline selects the strongest listed evidence; if Most dangerous takes that company's row chip, the caption explains the precedence. The not-profitable hunch line selects the most negative net worth, otherwise the largest relative 24-hour decline with a positive baseline, otherwise no company. That label is an inference from valuation, not measured rival profit. Float64 is used only to rank relative declines; monetary values remain integer pence.

Traffic combines the existing bounded 10,000-event sailing read and current quay notices over the last 24 real hours. Lanes are unordered port pairs; shared ports must be directly seen in `port_id`, not inferred from a route endpoint. `overlap_known` is false when own names are incomplete or no own notices were seen; overlap is then unknown, never zero, and the caption says so. Observed traffic coverage is partial regardless of own-name completeness; no observed notices means `not_observed`. Incomplete identity and truncated event reads are disclosed separately. Monopoly and loan evidence is bounded and limited by seven-day event retention. Goose migration `00010_rival_evidence.sql` adds `events_rival_evidence_idx ON events (account_id, created_at DESC, id DESC) WHERE event_type IN ('monopoly_granted','loan_request_posted')` inside the migration transaction. The build blocks event writes only for the milliseconds it takes over seven days of events, and deploys stop the previous bot first; it adds no rival-evidence table. The caption uses official valuation/next-refresh times, marks overdue publications and shows our measured daily change. Search, sorting and pagination retain their state across 30-second refreshes through stable company-name row keys. Piracy sponsors, attacks, blockades, dumping and rival profit are never inferred as facts; public marque sponsors are anonymous.

The company Journal merges recorded company events, whitelisted successful action outcomes, and durable settlements in one bounded, repeatable-read history query. Company scope is applied before the limit. The store selects lightweight action metadata first, then loads and projects one encrypted outcome at a time. Combined request/response ciphertext above 128 KiB is not loaded into this view; the entry honestly reports unavailable details while the original durable bytes remain intact. Lazy credential reads use the same transaction connection, so concurrent Journal reads never each wait for a second pooled connection. Raw request/response payloads are never returned. Transfers and collateral are labeled separately from revenue, and unknown-cost settlements never become zero-cost profit. A recorded action and its later settlement describe different facts, not two amounts to add together.

The interface separates fleet operations, money, trade, world conditions, and system diagnostics. Neutral charcoal and light surfaces share the same controls. The chart uses vendored Natural Earth 1:50m land, explicit port coordinates, and clearly labeled estimated ship positions. World conditions initially show active notices and fleet-relevant zones; visible scope controls retain access to the complete recorded set.

Overview shows account/company status, each ship's observed location and cargo, current blocker, and the controller's next recorded check directly. `_engine.holds`, `observed_at` and `next_check_at` describe a completed execution cycle in the matching snapshot generation; a fresh dashboard HTTP response alone is not executor liveness. A missing hold assessment is distinct from a completed assessment with no hold. Journal is chronological rather than a nested decision dump, with time, vessel, activity and cash visible together at the 640px layout. Initial map labels prioritize selected and occupied ports before nearby hubs and suppress overlaps. Money directly exposes owned underwriting collateral, premium entitlement, settled net and pilot allowance, including unverified funding holds; Exchange retains public policy listings.

Treasury, fleet-growth and underwriting control holds are company notices, not ships. Their current display attribution has no ship ID; durable decision records keep the internal control identity for diagnostics. Holds for actual ships retain their ship ID even when the corresponding fleet observation is unavailable.

Assessment coverage is explicit: `assessed_ship_ids` lists only ships actually visited in the matching completed generation. Work may return after one staged or consumed action; unvisited ships remain unassessed, not “no hold.” Current sourcing-budget and affordability blockers are attributed to their ship, while treasury, construction and underwriting blockers remain company notices.

## Readability

Source is written for maintenance, not compression. Use idiomatic multi-line Go, descriptive intermediate values, explicit error handling, and focused functions. Gofmt is mandatory but does not make semicolon-packed control flow acceptable. The same principle applies to TypeScript and migration SQL.
